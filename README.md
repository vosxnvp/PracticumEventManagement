# PracticumEventManagement

Учебный проект ASP.NET Core Web API для управления мероприятиями и бронированиями.

Проект выполнен в рамках курса «Продвинутая разработка на C# и .NET».

В проекте реализованы CRUD-операции для мероприятий, фильтрация и пагинация, создание и получение бронирований, ограничение количества мест, защита от овербукинга при конкурентных запросах, параллельная фоновая обработка заявок, глобальная обработка ошибок и юнит-тесты бизнес-логики.

## Технологии

- C#
- .NET 10
- ASP.NET Core Web API
- Swagger / OpenAPI
- LINQ
- xUnit
- `BackgroundService`
- `ConcurrentDictionary`
- `lock`
- `SemaphoreSlim`
- `Task.WhenAll`
- In-memory хранилище данных

## Модель мероприятия

Модель `Event` содержит:

- `Id` (`Guid`) — уникальный идентификатор мероприятия;
- `Title` (`string`) — название;
- `Description` (`string?`) — описание;
- `StartAt` (`DateTime`) — дата и время начала;
- `EndAt` (`DateTime`) — дата и время окончания;
- `TotalSeats` (`int`) — общее количество мест;
- `AvailableSeats` (`int`) — текущее количество свободных мест.

При создании мероприятия `AvailableSeats` автоматически устанавливается равным `TotalSeats`.

Значение `TotalSeats` обязательно и должно быть больше нуля.

Модель также содержит методы:

- `TryReserveSeats(int count = 1)` — пытается зарезервировать указанное количество мест и возвращает `false`, если свободных мест недостаточно;
- `ReleaseSeats(int count = 1)` — возвращает места в пул доступных.

## API мероприятий

### Получить мероприятия

```http
GET /events
```

Метод поддерживает фильтрацию и пагинацию с помощью query-параметров:

- `title` — фильтрация по названию мероприятия. Поиск регистронезависимый, поддерживается частичное совпадение;
- `from` — возвращаются мероприятия, которые начинаются не раньше указанной даты;
- `to` — возвращаются мероприятия, которые заканчиваются не позже указанной даты;
- `page` — номер страницы, значение по умолчанию `1`;
- `pageSize` — количество элементов на странице, значение по умолчанию `10`.

Все переданные фильтры применяются совместно.

Пример:

```http
GET /events?title=conference&from=2026-08-01&to=2026-08-31&page=1&pageSize=5
```

Пример ответа:

```json
{
  "totalCount": 1,
  "items": [
    {
      "id": "9f54215f-9acd-4bd8-9efc-c604d098a8fb",
      "title": "CSharp Conference",
      "description": "Конференция по C# и .NET",
      "startAt": "2026-08-10T10:00:00",
      "endAt": "2026-08-10T18:00:00",
      "totalSeats": 100,
      "availableSeats": 100
    }
  ],
  "page": 1,
  "count": 1
}
```

### Получить мероприятие по идентификатору

```http

```

Если мероприятие не найдено, возвращается:


## Бронирования

Модель `Booking` содержит:

- `Id` (`Guid`) — уникальный идентификатор бронирования;
- `EventId` (`Guid`) — идентификатор мероприятия;
- `Status` (`BookingStatus`) — текущий статус бронирования;
- `CreatedAt` (`DateTime`) — дата и время создания;
- `ProcessedAt` (`DateTime?`) — дата и время обработки.

Возможные значения `BookingStatus`:

- `Pending` — бронирование создано и ожидает обработки;
- `Confirmed` — бронирование подтверждено;
- `Rejected` — бронирование отклонено.

В текущей JSON-конфигурации значения перечисления сериализуются числами:

- `0` — `Pending`;
- `1` — `Confirmed`;
- `2` — `Rejected`.

### Создать бронирование

```http
POST /events/{id}/book
```

Создаёт бронирование для указанного мероприятия.

При успешном создании:

- проверяется наличие свободного места;
- `AvailableSeats` уменьшается на `1`;
- создаётся бронирование со статусом `Pending`;
- API сразу возвращает `202 Accepted`.

В теле ответа возвращается созданное бронирование, а в заголовке `Location` — ссылка на ресурс:

```text
Location: /bookings/{bookingId}
```

Пример ответа:

```json
{
  "id": "662a9942-b9a2-4fcd-b1f1-204144810033",
  "eventId": "7a509a49-1916-4956-9e6a-f5ea91e39d35",
  "status": 0,
  "createdAt": "2026-09-29T16:10:00Z",
  "processedAt": null
}
```

Если мероприятие не найдено, возвращается:

```text
404 Not Found
```

Если свободных мест больше нет, возвращается:

```text
409 Conflict
```

Пример ответа:

```json
{
  "title": "No available seats",
  "status": 409,
  "detail": "No available seats for this event"
}
```

### Получить бронирование по идентификатору

```http
GET /bookings/{id}
```

При успешном запросе возвращается:

```text
200 OK
```

Если бронирование не найдено, возвращается:

```text
404 Not Found
```

Пример ответа после фоновой обработки:

```json
{
  "id": "662a9942-b9a2-4fcd-b1f1-204144810033",
  "eventId": "7a509a49-1916-4956-9e6a-f5ea91e39d35",
  "status": 1,
  "createdAt": "2026-09-29T16:10:00Z",
  "processedAt": "2026-09-29T16:10:02Z"
}
```

## Защита от овербукинга

При создании бронирования необходимо атомарно выполнить две операции:

1. проверить наличие свободного места;
2. уменьшить `AvailableSeats` и создать бронирование.

Если несколько запросов выполнят эти действия одновременно без синхронизации, они могут зарезервировать одно и то же последнее место.

Для защиты критической секции в `BookingService` используется `lock`.

Под блокировкой выполняются:

- получение мероприятия;
- проверка наличия места через `TryReserveSeats()`;
- уменьшение `AvailableSeats`;
- создание бронирования;
- сохранение бронирования.

Благодаря этому только один поток одновременно проходит через критическую секцию и количество успешных бронирований не может превысить `TotalSeats`.

Операция чтения бронирования по `Id` блокировкой не защищается, поскольку не изменяет состояние доступных мест.

## Параллельная фоновая обработка бронирований

Обработка бронирований выполняется сервисом `BookingProcessingService` на базе `BackgroundService`.

Фоновый сервис периодически получает все бронирования со статусом `Pending` и запускает их обработку параллельно через `Task.WhenAll`.

Для каждой брони:

1. выполняется искусственная задержка около двух секунд, имитирующая внешний вызов;
2. задержка выполняется до захвата семафора, поэтому несколько заявок могут ожидать параллельно;
3. перед изменением состояния бронирования захватывается `SemaphoreSlim`;
4. если мероприятие существует, бронирование переводится в `Confirmed`;
5. если мероприятие удалено к моменту обработки, бронирование переводится в `Rejected` и в лог записывается предупреждение;
6. при неожиданной ошибке бронирование отклоняется, а зарезервированное место возвращается через `ReleaseSeats()`, если мероприятие всё ещё существует.

`SemaphoreSlim` используется вместо `lock`, потому что фоновая обработка содержит асинхронные операции с `await`.

Сервис корректно обрабатывает `OperationCanceledException` и завершает работу при остановке приложения.

## Пример сценария защиты от овербукинга

1. Создать мероприятие через `POST /events` с `"totalSeats": 3`.
2. Скопировать `Id` созданного мероприятия.
3. Выполнить `POST /events/{id}/book` три раза.
4. Все три запроса должны вернуть `202 Accepted`.
5. После трёх успешных бронирований `AvailableSeats` станет равным `0`.
6. Выполнить четвёртый `POST /events/{id}/book`.
7. Сервер вернёт `409 Conflict` с сообщением `No available seats for this event`.
8. Подождать несколько секунд.
9. Выполнить `GET /bookings/{bookingId}` для одной из успешных броней.
10. Статус изменится с `Pending` на `Confirmed`, а `ProcessedAt` будет заполнено.

## Валидация

При создании мероприятия проверяется:

- наличие `Title`;
- наличие `StartAt`;
- наличие `EndAt`;
- наличие `TotalSeats`;
- `EndAt` должен быть позже `StartAt`;
- `TotalSeats` должен быть больше `0`.

При обновлении мероприятия проверяется:

- наличие `Title`;
- наличие `StartAt`;
- наличие `EndAt`;
- `EndAt` должен быть позже `StartAt`.

Для пагинации проверяется:

- `page` должен быть больше или равен `1`;
- `pageSize` должен быть больше или равен `1`.

При ошибках валидации API возвращает:

```text
400 Bad Request
```

## Обработка ошибок

В приложении реализован глобальный middleware для централизованной обработки исключений.

Ошибки возвращаются в формате Problem Details.

### Ошибка валидации — 400

```json
{
  "title": "Validation error",
  "status": 400,
  "detail": "TotalSeats must be greater than zero."
}
```

### Ресурс не найден — 404

```json
{
  "title": "Resource not found",
  "status": 404,
  "detail": "Event with id 00000000-0000-0000-0000-000000000001 was not found."
}
```

### Нет свободных мест — 409

```json
{
  "title": "No available seats",
  "status": 409,
  "detail": "No available seats for this event"
}
```

### Непредвиденная ошибка — 500

```json
{
  "title": "Internal server error",
  "status": 500,
  "detail": "An unexpected error occurred."
}
```

Непредвиденные ошибки дополнительно логируются с использованием встроенного `ILogger`.

## Тесты

Бизнес-логика покрыта юнит-тестами с использованием xUnit.

После выполнения четвёртого спринта в проекте проходит `38` тестов.

Тесты `EventService` проверяют:

- создание мероприятия;
- заполнение `AvailableSeats` значением `TotalSeats` при создании;
- отклонение `TotalSeats <= 0`;
- получение всех мероприятий;
- получение мероприятия по идентификатору;
- обновление и удаление мероприятия;
- обработку несуществующих идентификаторов;
- фильтрацию по названию и датам;
- комбинированную фильтрацию;
- пагинацию;
- обработку некорректных дат и параметров пагинации.

Тесты бронирований проверяют:

- создание бронирования со статусом `Pending`;
- уменьшение `AvailableSeats` на `1`;
- создание нескольких бронирований до лимита мест;
- `NoAvailableSeatsException` после исчерпания мест;
- получение бронирования по `Id`;
- переходы в `Confirmed` и `Rejected`;
- заполнение `ProcessedAt` после `Confirm()` и `Reject()`;
- восстановление свободного места через `ReleaseSeats()`;
- повторное бронирование освобождённого места;
- создание бронирования для несуществующего или удалённого мероприятия;
- получение только необработанных бронирований со статусом `Pending`;
- защиту от овербукинга при `20` конкурентных запросах к мероприятию на `5` мест: ровно `5` успешных бронирований и `15` отказов;
- уникальность `Id` при `10` конкурентных запросах к мероприятию на `10` мест.

Конкурентные тесты используют реальный параллелизм через `Task.Run` и `Task.WhenAll`.

Для запуска всех тестов из корня репозитория:

```bash
dotnet test
```

## Хранение данных

После остановки и повторного запуска приложения созданные мероприятия и бронирования удаляются.

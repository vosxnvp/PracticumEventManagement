# PracticumEventManagement

Учебный проект ASP.NET Core Web API для управления мероприятиями и бронированиями.

Проект выполнен в рамках курса «Продвинутая разработка на C# и .NET».

В проекте реализованы CRUD-операции для мероприятий, фильтрация и пагинация, создание и получение бронирований, ограничение количества мест, защита от овербукинга при конкурентных запросах, параллельная фоновая обработка заявок, глобальная обработка ошибок и тесты бизнес-логики. С пятого спринта данные сохраняются в PostgreSQL через Entity Framework Core.

## Технологии

- C#, .NET 10 и ASP.NET Core Web API
- Entity Framework Core 10, провайдер Npgsql для PostgreSQL
- PostgreSQL 16 в Docker Compose
- Fluent API (`IEntityTypeConfiguration<T>`) для схемы таблиц и связей
- Swagger / OpenAPI
- LINQ и асинхронные запросы к базе данных
- `BackgroundService`, `IServiceScopeFactory`, `Task.WhenAll`
- `SemaphoreSlim` для синхронизации бронирований внутри одного процесса
- xUnit и EF Core InMemory для тестов

## Структура solution

Solution-файл `PracticumEventManagement.slnx` находится в корне репозитория и включает оба проекта:

- `PracticumEventManagement` — Web API;
- `PracticumEventManagement.Tests` — юнит-тесты.

Благодаря этому сборку и тесты можно запускать прямо из корня репозитория.

## Запуск проекта

Требования: **.NET SDK 10**, **Docker Desktop** с Linux-контейнерами (или Docker Engine и Compose) и свободный порт **5432**.

Клонировать репозиторий и перейти в его корень:

```bash
git clone https://github.com/vosxnvp/PracticumEventManagement.git
cd PracticumEventManagement
```

При проверке пятого спринта следует использовать ветку `sprint-5`:

```bash
git switch sprint-5
```

Запустить PostgreSQL из корня репозитория (там расположен `docker-compose.yml`):

```bash
docker compose up -d --wait postgres
docker compose ps
```

Compose запускает PostgreSQL 16 с базой `eventapi`, пользователем `postgres` и портом `5432`. Данные сохраняются в именованном Docker-томе `eventapi_pgdata`.

Строка подключения задаётся в `PracticumEventManagement/appsettings.json`, секция `ConnectionStrings:DefaultConnection`:

```json
{
  "ConnectionStrings": {
    "DefaultConnection": "Host=localhost;Port=5432;Database=eventapi;Username=postgres;Password=postgres"
  }
}
```

Здесь показана только секция подключения — остальные настройки JSON нужно сохранить. Пароль из примера предназначен исключительно для локального учебного окружения; для реальной эксплуатации используйте секреты/переменные окружения и отдельного пользователя БД.

Собрать решение и запустить тесты из корня:

```bash
dotnet build
dotnet test
```

Запустить API:

```bash
dotnet run --project PracticumEventManagement/PracticumEventManagement.csproj
```

В режиме Development Swagger UI доступен по адресу `http://localhost:5132/swagger` (точный адрес см. в выводе `dotnet run`).

**Создание схемы БД.** При запуске приложение вызывает `EnsureCreatedAsync()` через `AppDbContext`. При отсутствии таблиц EF Core создаёт `events`, `bookings`, внешний ключ и индекс по `event_id`. При повторном запуске существующие данные сохраняются. `EnsureCreatedAsync()` не выполняет миграции и не обновляет уже существующую схему: при последующих изменениях модели потребуются миграции EF Core или пересоздание учебной БД.

Для остановки API нажмите `Ctrl+C`. PostgreSQL можно остановить командой:

```bash
docker compose down
```

Команда не удаляет данные из тома. Не используйте `docker compose down -v`, если нужно сохранить записи.

## Модель мероприятия

Модель `Event` содержит:

- `Id` (`Guid`) — уникальный идентификатор мероприятия;
- `Title` (`string`) — название;
- `Description` (`string?`) — описание;
- `StartAt` (`DateTime`) — дата и время начала;
- `EndAt` (`DateTime`) — дата и время окончания;
- `TotalSeats` (`int`) — общее количество мест;
- `AvailableSeats` (`int`) — текущее количество свободных мест.

При создании мероприятия `AvailableSeats` автоматически устанавливается равным `TotalSeats`.

Значение `TotalSeats` обязательно и должно быть больше нуля. Для `StartAt` и `EndAt` используйте UTC-время (суффикс `Z`), поскольку PostgreSQL хранит даты в столбцах `timestamp with time zone`.

Модель также содержит методы:

- `TryReserveSeats(int count = 1)` — пытается зарезервировать указанное количество мест и возвращает `false`, если свободных мест недостаточно;
- `ReleaseSeats(int count = 1)` — возвращает места в пул доступных.

## API мероприятий

### Получить мероприятия

```http
GET /events
```

Метод поддерживает фильтрацию и пагинацию с помощью query-параметров:

- `title` — фильтрация по названию мероприятия. Поиск регистронезависимый, поддерживается частичное совпадение;
- `from` — возвращаются мероприятия, которые начинаются не раньше указанной даты;
- `to` — возвращаются мероприятия, которые заканчиваются не позже указанной даты;
- `page` — номер страницы, значение по умолчанию `1`;
- `pageSize` — количество элементов на странице, значение по умолчанию `10`.

Все переданные фильтры применяются совместно.

Пример:

```http
GET /events?title=conference&from=2026-11-01T00:00:00Z&to=2026-11-30T23:59:59Z&page=1&pageSize=5
```

Пример ответа:

```json
{
  "totalCount": 1,
  "items": [
    {
      "id": "9f54215f-9acd-4bd8-9efc-c604d098a8fb",
      "title": "CSharp Conference",
      "description": "Конференция по C# и .NET",
      "startAt": "2026-11-10T10:00:00Z",
      "endAt": "2026-11-10T18:00:00Z",
      "totalSeats": 100,
      "availableSeats": 100
    }
  ],
  "page": 1,
  "count": 1
}
```

### Получить мероприятие по идентификатору

```http
GET /events/{id}
```

Если мероприятие не найдено, возвращается:

```text
404 Not Found
```

### Создать мероприятие

```http
POST /events
```

Пример запроса:

```json
{
  "title": "Встреча команды",
  "description": "Обсуждение проекта",
  "startAt": "2026-11-10T10:00:00Z",
  "endAt": "2026-11-10T11:00:00Z",
  "totalSeats": 10
}
```

При успешном создании возвращается:

```text

```

Пример ответа:

```json

  "title": "Встреча команды",
  "description": "Обсуждение проекта",

  "endAt": "2026-11-10T11:00:00Z",
  "totalSeats": 10,
  "availableSeats": 10
}
```

### Обновить мероприятие

```http
PUT /events/{id}
```

Пример запроса:

```json
{
  "title": "Обновлённая встреча",
  "description": "Обновлённое описание",
  "startAt": "2026-11-10T12:00:00Z",
  "endAt": "2026-11-10T13:00:00Z"
}
```

При успешном обновлении возвращается:

```text

```

```text

```


При успешном удалении возвращается:

## Бронирования

Модель `Booking` содержит:

- `Id` (`Guid`) — уникальный идентификатор бронирования;
- `EventId` (`Guid`) — идентификатор мероприятия;
- `Status` (`BookingStatus`) — текущий статус бронирования;
- `CreatedAt` (`DateTime`) — дата и время создания;
- `ProcessedAt` (`DateTime?`) — дата и время обработки.

Возможные значения `BookingStatus`:

- `Pending` — бронирование создано и ожидает обработки;
- `Confirmed` — бронирование подтверждено;
- `Rejected` — бронирование отклонено.

API сериализует значения `BookingStatus` как строки `"Pending"`, `"Confirmed"`, `"Rejected"` через `JsonStringEnumConverter<BookingStatus>`. В PostgreSQL статус также хранится строкой благодаря `.HasConversion<string>()`.

### Создать бронирование

```http
POST /events/{id}/book
```

Создаёт бронирование для указанного мероприятия.

При успешном создании:

- проверяется наличие свободного места;
- `AvailableSeats` уменьшается на `1`;
- создаётся бронирование со статусом `Pending`;
- API сразу возвращает `202 Accepted`.

В теле ответа возвращается созданное бронирование, а в заголовке `Location` — ссылка на ресурс:

```text
Location: /bookings/{bookingId}
```

Пример ответа:

```json
{
  "id": "662a9942-b9a2-4fcd-b1f1-204144810033",
  "eventId": "7a509a49-1916-4956-9e6a-f5ea91e39d35",
  "status": "Pending",
  "createdAt": "2026-09-29T16:10:00Z",
  "processedAt": null
}
```

Если мероприятие не найдено, возвращается:

```text
404 Not Found
```

Если свободных мест больше нет, возвращается:

```text
409 Conflict
```

Пример ответа:

```json
{
  "title": "No available seats",
  "status": 409,
  "detail": "No available seats for this event"
}
```

### Получить бронирование по идентификатору

```http
GET /bookings/{id}
```

При успешном запросе возвращается:

```text
200 OK
```

Если бронирование не найдено, возвращается:

```text
404 Not Found
```

Пример ответа после фоновой обработки:

```json
{
  "id": "662a9942-b9a2-4fcd-b1f1-204144810033",
  "eventId": "7a509a49-1916-4956-9e6a-f5ea91e39d35",
  "status": "Confirmed",
  "createdAt": "2026-09-29T16:10:00Z",
  "processedAt": "2026-09-29T16:10:02Z"
}
```

## Защита от овербукинга

При создании бронирования сервис должен проверить наличие места, уменьшить `AvailableSeats` и создать запись `Booking`.

`BookingService` использует общий для экземпляров сервиса в пределах одного процесса `static SemaphoreSlim`: каждый запрос ожидает входа в критическую секцию через `WaitAsync()` с гарантированным освобождением в `finally`. Это позволяет использовать `await` при обращении к БД и предотвращает одновременное резервирование одного и того же последнего места внутри одного процесса приложения.

`Event` и новая `Booking` отслеживаются одним `AppDbContext`; один вызов `SaveChangesAsync()` сохраняет оба изменения. При отсутствии мест возвращается `409 Conflict`.

**Ограничение:** `SemaphoreSlim` не синхронизирует несколько экземпляров приложения на разных процессах/серверах. Для промышленной многосерверной системы необходима защита на уровне PostgreSQL (например, транзакции и блокировки строк либо контроль конкурентного обновления).

## Параллельная фоновая обработка бронирований

Обработка выполняется `BookingProcessingService` на базе `BackgroundService`. Сервис раз в секунду получает из PostgreSQL идентификаторы бронирований в состоянии `Pending` и запускает обработку параллельно через `Task.WhenAll`.

`BackgroundService` — singleton, а `AppDbContext` — scoped-зависимость. Поэтому сервис получает `IServiceScopeFactory` и создаёт отдельные DI-scope:

1. для получения списка идентификаторов `Pending` (после чтения scope закрывается);
2. для обработки каждой брони после имитации внешнего вызова с задержкой около двух секунд — каждый параллельный обработчик использует собственный `AppDbContext`.

Если бронь всё ещё имеет статус `Pending`, фоновый обработчик проверяет наличие мероприятия и переводит бронь в `Confirmed` (либо в `Rejected`, если мероприятие не найдено), устанавливает `ProcessedAt` и вызывает `SaveChangesAsync()`.

При непредвиденной ошибке предусмотрена попытка отклонить бронь и восстановить зарезервированное место, если событие существует. Отмена работы поддерживается через `CancellationToken`.

**Каскадное удаление:** внешний ключ `bookings.event_id` настроен с `ON DELETE CASCADE`. При удалении мероприятия PostgreSQL удаляет связанные бронирования; они не остаются в состоянии `Rejected`.

## Пример сценария защиты от овербукинга

1. Создать мероприятие через `POST /events` с `"totalSeats": 3`.
2. Скопировать `Id` созданного мероприятия.
3. Выполнить `POST /events/{id}/book` три раза.
4. Все три запроса должны вернуть `202 Accepted`.
5. После трёх успешных бронирований `AvailableSeats` станет равным `0`.
6. Выполнить четвёртый `POST /events/{id}/book`.
7. Сервер вернёт `409 Conflict` с сообщением `No available seats for this event`.
8. Подождать несколько секунд.
9. Выполнить `GET /bookings/{bookingId}` для одной из успешных броней.
10. Статус изменится с `Pending` на `Confirmed`, а `ProcessedAt` будет заполнено.

## Валидация

При создании мероприятия проверяется:

- наличие `Title`;
- наличие `StartAt`;
- наличие `EndAt`;
- наличие `TotalSeats`;
- `EndAt` должен быть позже `StartAt`;
- `TotalSeats` должен быть больше `0`.

При обновлении мероприятия проверяется:

- наличие `Title`;
- наличие `StartAt`;
- наличие `EndAt`;
- `EndAt` должен быть позже `StartAt`.

Для пагинации проверяется:

- `page` должен быть больше или равен `1`;
- `pageSize` должен быть больше или равен `1`.

При ошибках валидации API возвращает:

```text
400 Bad Request
```

## Обработка ошибок

В приложении реализован глобальный middleware для централизованной обработки исключений.

Ошибки возвращаются в формате Problem Details.

### Ошибка валидации — 400

```json
{
  "title": "Validation error",
  "status": 400,
  "detail": "TotalSeats must be greater than zero."
}
```

### Ресурс не найден — 404

```json
{
  "title": "Resource not found",
  "status": 404,
  "detail": "Event with id 00000000-0000-0000-0000-000000000001 was not found."
}
```

### Нет свободных мест — 409

```json
{
  "title": "No available seats",
  "status": 409,
  "detail": "No available seats for this event"
}
```

### Непредвиденная ошибка — 500

```json
{
  "title": "Internal server error",
  "status": 500,
  "detail": "An unexpected error occurred."
}
```

Непредвиденные ошибки дополнительно логируются с использованием встроенного `ILogger`.

## Тесты

Бизнес-логика покрыта юнит-тестами с использованием xUnit.

После выполнения пятого спринта в проекте проходят **40 тестов** (`dotnet test`). Тесты используют xUnit и EF Core InMemory; каждый тест получает изолированную базу с уникальным именем, а параллельные запросы используют отдельные DI-scope.

Тесты `EventService` проверяют:

- создание мероприятия;
- заполнение `AvailableSeats` значением `TotalSeats` при создании;
- отклонение `TotalSeats <= 0`;
- получение всех мероприятий;
- получение мероприятия по идентификатору;
- обновление и удаление мероприятия;
- обработку несуществующих идентификаторов;
- фильтрацию по названию и датам;
- комбинированную фильтрацию;
- пагинацию;
- обработку некорректных дат и параметров пагинации.

Тесты бронирований проверяют:

- создание бронирования со статусом `Pending`;
- уменьшение `AvailableSeats` на `1`;
- создание нескольких бронирований до лимита мест;
- `NoAvailableSeatsException` после исчерпания мест;
- получение бронирования по `Id`;
- переходы в `Confirmed` и `Rejected`;
- заполнение `ProcessedAt` после `Confirm()` и `Reject()`;
- восстановление свободного места через `ReleaseSeats()`;
- повторное бронирование освобождённого места;
- создание бронирования для несуществующего мероприятия;
- получение только необработанных бронирований со статусом `Pending`;
- защиту от овербукинга при `20` конкурентных запросах к мероприятию на `5` мест: ровно `5` успешных бронирований и `15` отказов;
- уникальность `Id` при `10` конкурентных запросах к мероприятию на `10` мест.

Конкурентные тесты используют `Task.Run` и `Task.WhenAll` с отдельным scope и `AppDbContext` для каждого запроса. Дополнительно проверяется работа контекста и связанных сущностей между разными scope. EF Core InMemory не проверяет реальные ограничения PostgreSQL и особенности SQL — их нужно проверять интеграционно.

Для запуска всех тестов из корня репозитория:

```bash
dotnet test
```

## Хранение данных

Основное хранилище — **PostgreSQL**, а не память процесса ASP.NET Core. Сервисы `EventService` и `BookingService` работают непосредственно с `AppDbContext` через `DbSet<Event>` и `DbSet<Booking>`.

Конфигурации `EventConfiguration` и `BookingConfiguration` в `DataAccess/Configurations` настраивают таблицы `events` и `bookings`, типы столбцов, первичные ключи (`Guid` генерируется приложением), строковое хранение `BookingStatus` и обязательную связь с каскадным удалением.

Данные остаются доступными после перезапуска API и остановки/повторного запуска контейнера PostgreSQL без удаления именованного тома.

Проверить таблицы можно командой:

```bash
docker compose exec postgres psql -U postgres -d eventapi -c "SELECT tablename FROM pg_tables WHERE schemaname = 'public' ORDER BY tablename;"
```

Проверить количество событий и броней:

```bash
docker compose exec postgres psql -U postgres -d eventapi -c "SELECT (SELECT COUNT(*) FROM events) AS events_count, (SELECT COUNT(*) FROM bookings) AS bookings_count;"
```

## Проверенный интеграционный сценарий

1. `POST /events` возвращает `201 Created` и создаёт мероприятие с `AvailableSeats = TotalSeats`.
2. `POST /events/{id}/book` возвращает `202 Accepted`, создаёт `Pending`-бронь и уменьшает число свободных мест.
3. Фоновый обработчик переводит бронь в `Confirmed` и записывает `ProcessedAt`; это видно в `GET /bookings/{id}` и PostgreSQL.
4. При исчерпании мест следующая попытка бронирования возвращает `409 Conflict`, лишняя запись не создаётся.
5. После перезапуска API события и бронирования остаются доступными.
6. `DELETE /events/{id}` возвращает `204 No Content`, после чего запросы удалённого события и связанных броней возвращают `404 Not Found`, а в PostgreSQL обеих записей больше нет.

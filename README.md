# PracticumEventManagement

Учебный проект ASP.NET Core Web API для управления мероприятиями и бронированиями.

Проект выполнен в рамках курса «Продвинутая разработка на C# и .NET».

В проекте реализованы CRUD-операции для мероприятий, фильтрация и пагинация, создание и получение бронирований, асинхронная фоновая обработка заявок, глобальная обработка ошибок и юнит-тесты бизнес-логики.

## Технологии

- C#
- .NET 10
- ASP.NET Core Web API
- Swagger / OpenAPI
- LINQ
- xUnit
- `BackgroundService`
- In-memory хранилище данных

## Запуск проекта

Клонировать репозиторий:

```bash
git clone https://github.com/vosxnvp/PracticumEventManagement.git
```

Перейти в каталог проекта:

```bash
cd PracticumEventManagement/PracticumEventManagement
```

Собрать проект:

```bash
dotnet build
```

Запустить приложение:

```bash
dotnet run
```

После запуска адрес приложения будет указан в консоли.

Swagger UI доступен по адресу:

```text
http://localhost:5132/swagger
```

Порт может отличаться в зависимости от настроек запуска.

## API

### Получить мероприятия

```http
GET /events
```

Метод поддерживает фильтрацию и пагинацию с помощью query-параметров:

- `title` — фильтрация по названию мероприятия. Поиск регистронезависимый, поддерживается частичное совпадение;
- `from` — возвращаются мероприятия, которые начинаются не раньше указанной даты;
- `to` — возвращаются мероприятия, которые заканчиваются не позже указанной даты;
- `page` — номер страницы, значение по умолчанию `1`;
- `pageSize` — количество элементов на странице, значение по умолчанию `10`.

Все переданные фильтры применяются совместно.

Пример фильтрации по названию:

```http
GET /events?title=conference
```

Пример фильтрации по датам:

```http
GET /events?from=2026-08-01&to=2026-08-31
```

Пример комбинированной фильтрации с пагинацией:

```http
GET /events?title=conference&from=2026-08-01&to=2026-08-31&page=1&pageSize=5
```

Пример ответа:

```json
{
  "totalCount": 2,
  "items": [
    {
      "id": "9f54215f-9acd-4bd8-9efc-c604d098a8fb",
      "title": "CSharp Conference",
      "description": "Конференция по C# и .NET",
      "startAt": "2026-08-10T10:00:00",
      "endAt": "2026-08-10T18:00:00"
    }
  ],
  "page": 1,
  "count": 1
}
```

### Получить мероприятие по идентификатору

```http
GET /events/{id}
```

Если мероприятие не найдено, возвращается:

```text
404 Not Found
```

### Создать мероприятие

```http
POST /events
```

Пример запроса:

```json
{
  "title": "Встреча команды",
  "description": "Обсуждение проекта",
  "startAt": "2026-08-10T10:00:00",
  "endAt": "2026-08-10T11:00:00"
}
```

При успешном создании возвращается:

```text
201 Created
```

### Обновить мероприятие

```http
PUT /events/{id}
```

Пример запроса:

```json
{
  "title": "Обновлённая встреча",
  "description": "Обновлённое описание",
  "startAt": "2026-08-10T12:00:00",
  "endAt": "2026-08-10T13:00:00"
}
```

При успешном обновлении возвращается:

```text
204 No Content
```

Если мероприятие не найдено:

```text
404 Not Found
```

### Удалить мероприятие

```http
DELETE /events/{id}
```

При успешном удалении возвращается:

```text
204 No Content
```

Если мероприятие не найдено:

```text
404 Not Found
```

## Бронирования

Модель `Booking` содержит:

- `Id` (`Guid`) — уникальный идентификатор бронирования;
- `EventId` (`Guid`) — идентификатор мероприятия, для которого создана бронь;
- `Status` (`BookingStatus`) — текущий статус бронирования;
- `CreatedAt` (`DateTime`) — дата и время создания бронирования;
- `ProcessedAt` (`DateTime?`) — дата и время обработки бронирования.

Возможные значения `BookingStatus`:

- `Pending` — бронирование создано и ожидает обработки;
- `Confirmed` — бронирование подтверждено;
- `Rejected` — бронирование отклонено.

В текущей JSON-конфигурации значения перечисления сериализуются числами:

- `0` — `Pending`;
- `1` — `Confirmed`;
- `2` — `Rejected`.

### Создать бронирование

```http
POST /events/{id}/book
```

Создаёт бронирование для указанного мероприятия.

При создании бронированию присваиваются уникальный `Id`, текущая дата и время в `CreatedAt` и статус `Pending`.

API не ожидает завершения обработки бронирования и сразу возвращает:

```text
202 Accepted
```

В теле ответа возвращается созданное бронирование, а в заголовке `Location` — ссылка на ресурс:

```text
Location: /bookings/{bookingId}
```

Пример ответа сразу после создания:

```json
{
  "id": "662a9942-b9a2-4fcd-b1f1-204144810033",
  "eventId": "7a509a49-1916-4956-9e6a-f5ea91e39d35",
  "status": 0,
  "createdAt": "2026-09-07T11:15:10.7141687Z",
  "processedAt": null
}
```

Если мероприятие не найдено, возвращается:

```text
404 Not Found
```

### Получить бронирование по идентификатору

```http
GET /bookings/{id}
```

Возвращает текущее состояние бронирования.

При успешном запросе возвращается:

```text
200 OK
```

Если бронирование не найдено, возвращается:

```text
404 Not Found
```

Пример ответа после фоновой обработки:

```json
{
  "id": "662a9942-b9a2-4fcd-b1f1-204144810033",
  "eventId": "7a509a49-1916-4956-9e6a-f5ea91e39d35",
  "status": 1,
  "createdAt": "2026-09-07T11:15:10.7141687Z",
  "processedAt": "2026-09-07T11:15:12.7931344Z"
}
```

## Фоновая обработка бронирований

Обработка бронирований выполняется отдельным сервисом на базе `BackgroundService`.

Фоновый сервис:

1. периодически получает бронирования со статусом `Pending`;
2. для каждого такого бронирования выполняет искусственную задержку около двух секунд, имитируя обращение к внешней системе;
3. переводит бронирование в статус `Confirmed`;
4. заполняет поле `ProcessedAt`.

Таким образом, создание бронирования реализует паттерн «быстрый ответ + отложенная обработка»: клиент сразу получает `202 Accepted`, а дальнейшая обработка выполняется в фоне.

Фоновый сервис использует `CancellationToken` и корректно завершает работу при остановке приложения.

## Пример сценария бронирования

1. Создать мероприятие через `POST /events`.
2. Скопировать `Id` созданного мероприятия.
3. Выполнить `POST /events/{id}/book`.
4. Получить `202 Accepted`, заголовок `Location` и бронирование со статусом `Pending`.
5. Выполнить `GET /bookings/{bookingId}` сразу после создания — бронирование будет находиться в состоянии `Pending`.
6. Подождать несколько секунд.
7. Повторно выполнить `GET /bookings/{bookingId}` — статус изменится на `Confirmed`, а поле `ProcessedAt` будет заполнено.

## Валидация

При создании и обновлении мероприятия проверяется:

- наличие `Title`;
- наличие `StartAt`;
- наличие `EndAt`;
- `EndAt` должен быть позже `StartAt`.

Для пагинации проверяется:

- `page` должен быть больше или равен `1`;
- `pageSize` должен быть больше или равен `1`.

При ошибках валидации API возвращает:

```text
400 Bad Request
```

## Обработка ошибок

В приложении реализован глобальный middleware для централизованной обработки исключений.

Ошибки возвращаются в едином формате Problem Details.

### Ошибка валидации — 400

```json
{
  "title": "Validation error",
  "status": 400,
  "detail": "EndAt must be later than StartAt."
}
```

### Ресурс не найден — 404

```json
{
  "title": "Resource not found",
  "status": 404,
  "detail": "Event with id 00000000-0000-0000-0000-000000000001 was not found."
}
```

### Непредвиденная ошибка — 500

```json
{
  "title": "Internal server error",
  "status": 500,
  "detail": "An unexpected error occurred."
}
```

Непредвиденные ошибки дополнительно логируются с использованием встроенного `ILogger`.

## Тесты

Бизнес-логика `EventService` и `BookingService` покрыта юнит-тестами с использованием xUnit.

Тесты `EventService` проверяют:

- создание мероприятия;
- получение всех мероприятий;
- получение мероприятия по идентификатору;
- обновление мероприятия;
- удаление мероприятия;
- обработку несуществующих идентификаторов;
- фильтрацию по названию;
- фильтрацию по датам;
- комбинированную фильтрацию;
- пагинацию;
- обработку некорректных дат;
- обработку некорректных параметров пагинации.

Тесты `BookingService` проверяют:

- создание бронирования для существующего мероприятия со статусом `Pending`;
- создание нескольких бронирований с уникальными `Id`;
- получение бронирования по `Id`;
- изменение состояния бронирования на `Confirmed`;
- изменение состояния бронирования на `Rejected`;
- создание бронирования для несуществующего мероприятия;
- создание бронирования для удалённого мероприятия;
- получение несуществующего бронирования;
- подтверждение и отклонение несуществующего бронирования;
- получение только необработанных бронирований со статусом `Pending`.

Для запуска всех тестов из каталога solution выполните:

```bash
dotnet test
```

## Хранение данных

Данные о мероприятиях и бронированиях хранятся в памяти приложения.

После остановки и повторного запуска приложения созданные мероприятия и бронирования удаляются.
